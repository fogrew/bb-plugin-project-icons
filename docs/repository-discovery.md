# Repository icon discovery

The image editor has a **Find icons in repository** button. Nothing is searched until it is pressed.

- Search uses the supported SDK `projects.files` and `projects.fileContent` calls, which route to the project's own host. No network access is added by the plugin.
- Six queries (`favicon`, `icon`, `logo`, `apple-touch`, `android-chrome`, `ic_launcher`) run in parallel with a combined 8 s timeout. Results are filtered to PNG, JPEG, WebP and ICO files, skipping dependency/build/tool directories (`node_modules`, `dist`, `build`, `bin`, `obj`, `.claude`, …), paths deeper than 8 segments, absolute or `..` paths, backslashes and control characters. At most 12 ranked candidates are shown.
- A file qualifies when its name contains `favicon`, `icon`, `logo`, `apple-touch`, `android-chrome` or `ic_launcher` (covers `app-icon`, `icon-512.png`, `Square310x310Logo.png`, `AppIcon` sets), or when it is a size-only name (`128x128.png`, `128x128@2x.png`, `512.png`) inside an icon directory (`icons`, `logos`, `favicons`, `app-icon(s)`, Android `mipmap-*`, `*.appiconset`, `*.iconset`; this covers `src-tauri/icons/`). Other images in such directories (for example `icons/arrow.png`) are not suggested. Size-only names are found only if the host's file search returns them for one of the queries (not verified live).
- `build/` is ignored as build output with one exception: `build/icon.*` and `build/icons/` at the repository root (the electron-builder convention). Directories below that prefix are still checked against the ignore list (`build/icons/dist/…` is skipped). Nested `build/` directories in monorepo packages are not covered.
- Ranking: `favicon*` first, then `logo*`/`app-icon`/`apple-touch`/`android-chrome`/`ic_launcher`, then other `logo`, `icon*` and size-only names. Within a name class, larger square sizes rank above smaller ones (`512` before `192` before `16`), names without a size are treated like ~128 px, and non-square names are demoted. Sizes are read from the file name only (`@2x`/`@3x` multiply the size; a lone number that looks like a year, 1990-2099, is not a size); Android `mipmap-*`/`drawable-*` density directories act as a size tier (`xxxhdpi` before `xxhdpi` … before `mdpi`), and `ic_launcher_round`/`_foreground`/`_background`/`_monochrome` rank below plain `ic_launcher`. An `.ico` ranks like a PNG with the same name, so `favicon.ico` sits between `favicon-192x192.png` and `favicon-32x32.png`, and it yields a tie to an equally ranked PNG in the same directory (a half-step penalty). No extra file contents are read at ranking time.
- SVG and other formats (GIF, BMP, AVIF, TIFF) with a matching name are counted and reported as skipped; SVG is never rendered.
- Reading a candidate re-validates the path, rejects files over 2 MB, requires base64 content whose magic bytes match a supported format and the file extension (an `.ico` may contain ICO, PNG, JPEG or WebP data; a `.png`, `.jpg` or `.webp` must not contain ICO data), then hands the bytes to the existing editor as a draft. ICO files are validated and reduced to one image first (see below). The existing icon changes only after the user presses Save.
- A missing folder, an offline host or a timeout is reported as unavailable; zero matches show an explicit empty state. Switching projects or closing the editor discards in-flight results.
- The button is available whether or not the project already has an icon; the existing icon changes only on Save (`repository-icons.browser.mjs` covers this).

## ICO files

`.ico` is accepted for repository candidates and for manual choose, drop and paste. The same validator (`lib/ico.ts`) runs on the host in `readCandidate` and again in the browser before decoding, so a hostile file is rejected on both sides.

- The whole file is rejected when the header is not reserved `0` and type `1` (cursors, type `2`, are not icons), the entry count is `0` or above 64, the directory does not fit in the file, any entry has size `0`, starts inside the directory or ends past the end of the file, or the file exceeds the size limit (2 MiB on the host, the editor's 2,000,000 bytes for manual import; both are the existing limits).
- An entry is usable only if its payload is a PNG with a valid color type and bit depth whose IHDR (13-byte chunk) dimensions equal the directory dimensions (a directory value of `0` means 256) and pass the same pixel bound as peer images, or a BMP/DIB with a 40-byte `BITMAPINFOHEADER`, matching width, doubled height, one plane, 1, 4, 8, 24 or 32 bits, no compression and complete pixel and mask data. Anything else is skipped, not fatal: 16-bit BMPs, RLE or other compressed and bitfield BMPs, BMPs with a V4/V5 or any other non-40-byte header, JPEG or SVG payloads, truncated data, and oversize or mismatched dimensions. The next-largest usable entry is tried instead.
- The largest usable entry wins: by pixel area, then bit depth read from the entry's own PNG or DIB header (the directory's bit count is ignored), then directory order, so the choice does not depend on how the sizes are arranged. If the largest entry is unusable the next one is tried; if none is usable the file is rejected with "Icon file has no usable image".
- A PNG entry is handed on as `image/png`. A BMP entry is wrapped, byte for byte, into a single-image ICO (`image/x-icon`) and decoded by the browser; the plugin does not decode DIB pixels itself.
- Either result goes through the existing path: browser decode, crop preview and the 64 x 64 PNG export with its 64 KiB check. The existing icon changes only on Save.
- A file named `.ico` may hold PNG, JPEG or WebP data instead of ICO data (common in the wild, for example a renamed PNG). The content is sniffed, passes the peer pixel bound (4096 px per side, 16 megapixels) and is handled as that format, with the usual 64 x 64 PNG output; this works the same in `readCandidate`, choose and drop. The reverse is refused: ICO content named `.png`, `.jpg` or `.webp` is rejected, as is ICO-typed or ICO-content input without an `.ico` name. The file picker lists `.ico`, `image/x-icon` and `image/vnd.microsoft.icon`.
- Pasted ICOs are not accepted unless the pasted file keeps an `.ico` name: clipboard image data normally arrives as `image.png` or without a name and is refused if it is ICO data. Dropped or chosen files are checked the same way.
- Homepage and other plugin artwork is unchanged: SVG and ICO stay rejected there.

## Verification boundary

Covered by unit tests (`discovery.test.mjs`, `ico.test.mjs`, `image-input.test.mjs`) and a real-Chrome fixture (`repository-icons.browser.mjs`) with SDK and RPC mocked. The fixture builds multi-size ICOs in code (`test-fixtures/ico.mjs`), imports one through **Find icons in repository** and others through the file picker, and checks the saved 64 x 64 PNG's pixels in real Chrome; the `readCandidate` reply it serves is produced by the real validator but travels over the mocked RPC. BMP entries rely on the browser's own ICO decoder, which was exercised in Chrome only; other engines and real-world `favicon.ico` files were not tried. Not verified live in BB: how the host's fuzzy `projects.files` query ranks and truncates results in large repositories (it is queried with `limit` 300 per query), real multi-logo repositories, remote hosts, symlink escapes (containment is the host API's responsibility; the plugin cannot observe symlinks) and the host's own size limits (`fileContent` reports `sizeBytes` after the read, so an oversized file is read by the host before being rejected).

An unknown project makes `discover` and `readCandidate` fail with "Project not found". Host error details are logged, not returned to the UI.
